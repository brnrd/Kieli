# Install Keylo in your AWS account

This installer provisions a **single-organization, self-hosted** Keylo stack. You own the AWS resources and pay AWS directly. It does not create a subscription, billing service, or shared SaaS workspace.

The installer and release workflow are implemented. **No release account or artifact bucket is configured in this checkout, so there is no live Deploy button yet.** Maintainer publishing is a separate step described below. Nothing in the local build deploys AWS resources.

## Customer installation

For a published release:

1. Open its **Deploy Keylo** link for the desired AWS region. Review the linked CloudFormation template and the release checksum/source revision before launching.
2. Sign in to your AWS account, choose a unique stack name, and leave `AuthMode=local` and `AppOrigin` empty for the simplest install. Review the resources, IAM permissions, and normal AWS charges, then create the stack.
3. After the stack reaches `CREATE_COMPLETE`, open **Outputs → Url**. The generated HTTPS origin is configured automatically in the same deployment.
4. Open **SetupSecretConsole**, find the secret identified by **SetupSecretArn**, and retrieve its JSON value. Copy only the `token` field into Keylo's setup form. Your AWS identity needs permission to retrieve that secret.
5. Enter your name, administrator email, and a strong password. Keylo atomically creates the first administrator and signs you in. You can now create/import projects and invite teammates.

You do not need local Node, Docker, SAM, or a database server. The default stack includes a Node.js 24 Lambda function, AWS Lambda Web Adapter layer, HTTP API Gateway, DynamoDB, bounded CloudWatch logs, and the first-run secret. There is no VPC/NAT gateway or always-on database instance. The browser is still required to approve AWS permissions/costs and set the administrator's password; “one-click” describes the guided infrastructure install, not bypassing those steps.

The setup secret is generated by AWS Secrets Manager and is not a password or sign-in credential. It never appears in the launch link, page HTML, CloudFormation output values, or application logs. Keylo reads the current value server-side, checks it with a constant-time digest comparison, and rate limits attempts. Weak passwords or invalid secrets do not claim the workspace. Competing requests cannot create multiple initial administrators. After either web installation or operator bootstrap, the shared control record closes web installation permanently; changing the setup secret cannot reopen it. Keep the setup secret managed by its CloudFormation stack; its token remains unusable after completion. Retain ordinary administrator recovery access through the documented operator workflow.

The first-run form is enabled only for local accounts with `KEYLO_INSTALL_SECRET_ARN` configured. `KEYLO_INSTALL_TOKEN` is a development-only fixture option and is ignored in production. Ordinary Docker/source installations continue to use the operator bootstrap CLI. The installer introduces no public “first visitor becomes admin” behavior.

## Optional SSO and custom domain

The CloudFormation parameters also support `AuthMode=okta` or `saml`. Those choices require your existing IdP configuration and an appropriate Secrets Manager secret; CloudFormation rules reject missing required SSO parameters. SSO installs use verified group assignments and do not open local administrator setup. See [OIDC](okta.md) and [SAML](saml.md).

To switch a local install to SSO later, first assign at least one trusted IdP principal the `keylo-admin` group, configure the IdP callback/recipient for this deployment, then update the stack with the matching parameters and verify sign-in. There is no automatic account linking by email. Switching back to local accounts preserves the existing local users and does not rerun installation. If SSO was used from the beginning and no local admin was ever initialized, an explicit switch to local creates a fresh AWS setup secret and enables the first-run form.

For a custom domain, set up API Gateway's domain mapping, DNS, and ACM certificate, then update `AppOrigin` to the exact HTTPS origin. The installer does not manage an external DNS provider or an IdP account. Keep previous SSO parameters when updating. See [AWS operations](aws.md).

## Upgrades, rollback, and deletion

Published application ZIPs and templates are versioned. Templates pin the exact S3 object version for code; launch URLs pin the template's version as well. Normal publishing refuses to replace a different artifact at an existing release path. Releases are built on Linux x64 with glibc and verify the native Argon2 binary. A macOS/local QA package is explicitly non-publishable.

To upgrade, open the **existing stack**, create an update/change set using the new published template, keep its current authentication/domain parameters, and review all changes before execution. The logical data table, its retention/deletion protection/PITR settings, and the initialization control remain unchanged. A code update does not create another administrator. Keep a tested backup and restore policy; use a prior compatible template for code rollback. Future schema changes must document their compatibility and migration steps before release.

The older source-built image stack in `infra/template.yaml` remains supported separately. Do not replace an existing image stack with the ZIP installer template without a reviewed migration. This release does not automate image-to-ZIP conversion or data migration.

Deleting the stack **retains the DynamoDB table**, with deletion protection. Remove retained data only through a deliberate separate AWS operation. The application and log groups are removed with their stack resources. A setup secret deleted with the stack is not an account-recovery mechanism. Record the data-table name and use [built-in account recovery](built-in-accounts.md) when necessary.

The current API throttles are 20 requests/second, burst 40. Lambda uses account-default concurrency initially, so accounts with reduced new-account quotas can install. After checking your regional quota, set the optional `ReservedConcurrency` parameter to a positive limit (for example 20); `0` leaves reservation unset. Log retention is 14 days. Review these limits and the AWS region against your workload. AWS billing is usage-based; there is no fixed-price hosting charge from Keylo.

## Maintainer: configure publishing later

The `.github/workflows/aws-release.yml` workflow always builds/tests/packages a release on Linux. Without `AWS_RELEASE_TARGETS`, it uploads the package as a workflow artifact and explicitly reports publishing as unconfigured. It does not generate a pretend public install link or contact AWS.

When a release AWS account is available:

1. Use a dedicated artifact account/bucket. Deploy `infra/release-publisher.yaml` in each publishing region with the exact `GitHubRepository` (`owner/repository`). For additional regions in the same account, pass the first stack's `OidcProviderArn` as `ExistingGitHubOidcProviderArn`.
2. This maintainer template deliberately makes only `releases/*` readable publicly, because the template and open-source ZIP need to be installable in other accounts. Its bucket is versioned, encrypted, and retained; public ACLs remain blocked and HTTPS is enforced. It must never contain customer data or credentials. Account-level S3 public-policy controls must permit this designated public artifact bucket; use the organization's approved artifact-hosting account rather than changing unrelated account guardrails.
3. Create a protected GitHub environment named `aws-release`, restrict approved release branches/tags and maintainers, and set repository variable `AWS_RELEASE_TARGETS` to a JSON array using the publisher stack's outputs:

   ```json
   [{"region":"eu-west-1","bucket":"YOUR_RELEASE_BUCKET","roleArn":"arn:aws:iam::YOUR_ACCOUNT_ID:role/YOUR_PUBLISHER_ROLE"}]
   ```

4. Run **Package AWS installer** manually, or publish a GitHub release whose tag exactly matches `v<package.json version>`. Use a new version for changed code, templates, or publishing metadata. Untrusted pull requests cannot obtain the publisher role: GitHub OIDC trust is restricted to this exact repository and protected environment, and the packaging job has no OIDC publishing permission.
5. The publishing job verifies checksums, uploads immutable/versioned code, validates the regional template with AWS, and publishes the template and manifest. Its summary and downloadable `keylo-launch-<region>` artifact include the real **Deploy Keylo** link and a reviewable template URL. Add those links to the release notes/README after successful publishing. No long-lived AWS access keys are needed.

Each region needs its own artifact bucket because Lambda ZIP code must come from S3 in the function's region. The generated template includes only that region's artifact mapping, so it cannot silently install code from another region. Start with `eu-west-1`; publish more regions only after checking Node.js 24 and the pinned public adapter layer there.

The source for the customer template is `infra/install-template.mjs`. `scripts/render-aws-template.mjs` renders an **unpublished example for schema checks**, not a working installer. `scripts/package-aws.mjs` traces runtime dependencies and copies static assets/licenses into an 11 MiB-class ZIP rather than including the source checkout, test data, development tools, or local secrets. The package-size guard reserves room below Lambda's uncompressed code/layer limit. `scripts/publish-aws.mjs` emits the regional template and launch URL after receiving real S3 version IDs. No customer-resource credentials or telemetry are sent to a Keylo-operated service.

## Validation

```sh
npm run check
npm test
npm run build
npm run smoke:install
```

The installer smoke builds a local QA ZIP, extracts it into a clean temporary directory, executes its startup script, serves the compiled application, and exercises first-run setup over HTTP with a disposable database. It covers static assets, native password hashing, origin checks, invalid/weak credentials, racing initializers, authenticated project creation, and permanent closure. Existing demo/local/SAML/MCP smoke suites remain part of the release workflow. Infrastructure tests cover dependency cycles, retention, scopes, immutable artifacts, and launch-link encoding; `cfn-lint` validates both templates. One known optional-ARN constraint inference warning (`W1030`) is suppressed in the generated template; required SSO ARN rules and exact IAM resources are explicitly checked.

A real clean-account AWS install/upgrade, regional artifact access, Secrets Manager permissions, Lambda's managed runtime/layer, and DynamoDB transaction behavior still require integration verification before advertising the installer as production-ready. No live AWS integration run has been performed in this checkout.

References: [CloudFormation quick-create links](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-console-create-stacks-quick-create-links.html), [Lambda ZIP deployment](https://docs.aws.amazon.com/lambda/latest/dg/configuration-function-zip.html), [Lambda Web Adapter](https://github.com/aws/aws-lambda-web-adapter).

## Optional SSO lifecycle configuration

Both templates accept `SsoProvisioningMode=jit|scim`, `ScimSecretArn` (plain provisioning token; required in SCIM mode), and `ReconciliationSecretArn` (JSON with `origin`, `appId`, `apiToken`). These options require OIDC or SAML. Secrets are operator-supplied and are never template outputs. The runtime receives read permission only for the configured secret ARNs; custom KMS keys need a separately scoped decrypt grant. When reconciliation is configured, the five-minute maintenance runner invokes it alongside snapshots, with bounded work and resumable progress. See [SSO lifecycle setup and limitations](sso-lifecycle.md) before enabling SCIM; provision an administrator and its pushed group first.
